# 0.2.0

_In development. Not yet released._

Querydown 0.2.0 can query tables in any schema of your database, as in `#/billing/invoices`, with relationships across schemas. The language has no breaking changes: queries written for 0.1.0 still work as they did.

## Who needs to change anything

| If you… | Do you need to change anything? |
| -- | -- |
| Write queries | **No.** The language only gained syntax. |
| Write schema JSON by hand | **No.** A schema written for 0.1.0 means the same as before. |
| Use the command line tool | **No.** |
| Use the JavaScript package | **No.** Where it takes a base table, it now also takes a list of names. |
| Use the CodeMirror package | **No.** |
| Generate the schema JSON with introspection | **Check.** It now finds the tables of every schema, not only `public` or `main`. See [below](#introspection-reads-every-schema). |
| Use the Rust crates' syntax tree, or complete sections in Rust | **Yes.** Table names there have a type of their own. See [below](#table-names-in-the-rust-syntax-tree). If you only compile query text, nothing changes. |

## How to get it

See [installation](../../../docs/setup/installation.md).

## What's new

- **Tables in other schemas.** A table in the current schema is written as before, as in `#clients`. A table in another schema is written with the schema's name first, as in `#/billing/invoices`. It can go anywhere a table can: as a base table, among related records, and in definitions. See [tables in other schemas](../../../docs/language.md#tables-in-other-schemas).

    > Each client, with their total of unpaid invoices

    ```qd
    #clients $name $#/billing/invoices{is_paid:@false}.amount%sum -> unpaid
    ```

- **Nested schemas.** A table can have more than one name before its own. In DuckDB, a table of another attached database is written with the database's name and then the schema's, as in `#/archive/main/orders`.
- **Relationships across schemas**, in both directions, just as within one.
- **Tables of the same name** in different schemas are kept apart, along with their computed columns and custom comparisons. When a table isn't found, the error suggests any tables of that name in other schemas.
- **A `schema` in the schema JSON**, for tables and for the ends of links. It's absent for a table in the current schema. See [schemas](../../../docs/setup/introspection.md#schemas).
- **Introspection reads every schema**, and every database attached to DuckDB, along with the foreign keys between them. See [below](#introspection-reads-every-schema).
- **Highlighting and autocompletion** know tables in other schemas. After a `#`, completion offers them too, as in `/billing/invoices`.
- **Less repeated work in the SQL.** When a query needs the same aggregate of related records more than once, the SQL computes it once. Before, the two bounds of `#comments:1..5` each counted the comments, and a [computed column](../../../docs/language.md#computed-columns) such as `#issues.n_comments = #comments`, used as a condition, a sort, and a result column, counted them three times.
- **For applications:**
    - In Rust, `querydown::parse_table_name` reads a table's name as it's written after a `#`.
    - In JavaScript, [`compile_sections`](../../../docs/setup/javascript.md#compile_sections) and the completer's `baseTable` option take a list of names for a table in another schema, as in `["billing", "invoices"]`.
    - In the CodeMirror package, `baseTable` can be such a list too, and its type is exported as `TableName`.
- **The sample schema** has a table in another schema, `billing.invoices`, so you can try all this in the [playground](/playground).

## Fixes

- **PostgreSQL identifiers that contain a `"`** are quoted correctly. Before, the compiler escaped the `"` with a backslash, and PostgreSQL rejected the SQL. Now the `"` is doubled.

## Changes that break things

These change the behavior of queries or code written for the previous release.

### Introspection reads every schema

In 0.1.0, introspection read only one schema: `public` in PostgreSQL, and `main` in DuckDB. Now it reads them all, so the schema JSON it generates can differ from before:

- **It has more tables.** If your database has tables in other schemas, the compiler and autocompletion now know them, and your users can query them. If they shouldn't, remove those tables from the schema JSON before you create the compiler, as you would any other table. See [adjust the schema](../../../docs/setup/introspection.md#adjust-the-schema).
- **In PostgreSQL, the current schema is the first one on the search path**, not always `public`. Usually that's `public` anyway. If yours isn't, the tables of `public` now have a `schema`, and queries name them as in `#/public/issues`.
- **In DuckDB, the tables of attached databases have a `schema`.** In 0.1.0, the tables in the `main` schema of every attached database were listed as if they were in the current schema. Now they're named with their database, as in `#/archive/main/orders`.

The JSON for a database with a single schema is the same as before.

### Table names in the Rust syntax tree

In the `querydown` and `querydown-parser` crates, a table's name in the syntax tree is now an `ast::TableName`, not a `String`. It holds the table's `name` and its `schema`, which is empty for a table in the current schema. That's the type of:

- `Query.base_table` and `UnionMember.base_table`
- `ComputedColumn.table` and `CustomComparisonDef.table`
- `TableWithMany.table`, and what `PathPartKind::TableWithOne` holds

For completion, `CompletionRequest.base_table` is now an `Option<&TableName>`.

To update your code:

- To make a `TableName` for a table in the current schema, use `TableName::new("issues")` or `"issues".into()`. For another schema, use `TableName::in_schema(vec!["billing".to_string()], "invoices")`, or `parse_table_name("/billing/invoices")`.
- `Query::from_parts` still accepts a `String` for the base table. See [compile a query in sections](../../../docs/setup/rust.md#compile-a-query-in-sections).
- A `TableName` still equals a `&str` or `String` with the same name, when it's in the current schema. For the name alone, read its `name`. To show it as it's written in Querydown, as in `/billing/invoices`, format it with `Display`.
